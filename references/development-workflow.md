# AI App 七阶段开发流程

默认一个项目使用 applications/<appCode>/ 管理多个应用，详细结构见 [目录规则](application-manifest.md#项目与多应用目录)。资源范围包括 Web、自定义对象及字段、自定义类、智能体、技能、知识库、MCP 服务及工具。按需求选择，不要求每个应用创建全部资源；本流程暂不扩展触发器或定时类。

## 1. 需求讨论

先读取现有应用文档和会话已确认信息，再讨论业务目标、使用场景、输入输出、业务步骤、数据存储、AI行为和验收标准。将结果写入应用自己的 docs/requirements.md，不只留在聊天记录中；后续变更同步修订，不重复询问已确定事项。

## 2. 实现设计

在 docs/design.md 中明确 Web 页面和交互、对象字段关系、类方法与参数返回、智能体职责与模型、技能规则、知识资料范围、所需 MCP 工具及资源关联。记录每项资源复用或新建的理由、依赖顺序、异常处理和验收方式。知识资料是否属于可分发应用内容须单独明确，不将测试资料或真实客户数据自动打包。

在设计任何自定义类、对象或字段之前，先按 [CloudCC资源开发前置要求](../SKILL.md#cloudcc-资源开发前置要求) 执行对应资源的 introduction 与 devguide 两条文档命令，实际读取资源介绍和开发指南，再开始设计；涉及多类资源时逐类执行，不能仅凭已有示例先写设计或源码。继续读取专用技能要求的平台能力文档，遵循标准能力优先与 API Name 引用，不用源组织内部 ID 作为可分发标识。

## 3. 启动项目与两套凭据

开发前检查两套配置，不能互相替代：

| 配置 | 位置 | 用途 |
| --- | --- | --- |
| cloudcc-agentcici.config.json | 项目根目录，多应用共享 | AgentCiCi 开发者换票，管理智能体、技能、知识库、MCP和应用 |
| cloudcc-cli.config.json | 项目根目录，多个应用共用 | CRM 开发者配置，创建/发布对象字段和自定义类 |
| .cloudcc-cache.json | 项目根目录，与共用CRM配置同目录 | CLI管理的当前CRM环境身份和accessToken，仅本地联调使用 |

CRM配置和缓存统一在项目根目录，代码仍位于各应用内，具体CLI调用与已有项目归并规则见 [多应用共用CRM配置](cloudcc-shared-config.md)。不在应用目录复制配置，也不把代码搬到根目录。两套配置的 use 独立，启动前核对目标地址、环境和组织是否符合本次设计，不能只看环境名称相同就认定身份一致。认证缺失只补缺失的那一套。所有真实配置、缓存、本地运行Key与资料均加入Git忽略；不写进应用清单、Web源码或发布包。

配置AgentCiCi身份按 [认证说明](authentication.md)；配置CloudCC身份按专用技能 platform/project devguide 和CLI要求，先检查provider，不把AgentCiCi的clientSecret填入CloudCCDev，也不把CRM accessToken用于AgentCiCi开发者换票。

## 4. 开发与资源关联

- 在 src/ 本地开发 Web，通过宿主SDK获取生产CRM上下文，采用 Web → 自定义类 → 对象的数据调用方式。
- 按对象→字段→类依赖顺序，通过CloudCC CLI创建资源；对象命令生成plan时继续按CLI规则显式apply并回读，不把plan成功当作创建成功。类通过本技能共用配置适配入口调用CLI，在应用内创建backend/classes目录，只编辑SOURCE区域，进行格式检查、真实平台模板编译、开发组织发布及源码回读。
- 通过AgentCiCi技能命令创建/复用所需技能并编译发布；创建/复用知识库，上传用户授权资料，发布索引并查询文档状态、测试检索，见 [知识库管理](knowledge-bases.md)。不杜撰知识数据或把文件上传成功当作索引完成。
- 按需配置MCP服务、发现和读取真实工具schema，然后选用所需工具；MCP详细规则和CloudCC两个服务地址见 [MCP工具](mcp-tools.md)。先检查已有服务避免重复，不根据地址猜认证、工具名称或参数。
- 创建/复用应用智能体，读取现状后将技能、知识库和工具关联进去；三类关联都需要保存真实ID/工具名。保留其他已有绑定，核对技能toolWhitelist/kbWhitelist，最后编译并发布本次返回的智能体版本。资源创建、关联、编译、发布是不同状态。
- 资源定义、无凭据的MCP声明、绑定映射和验证结果保存在应用内；开发环境ID作为本地关联记录，交付用逻辑ref及原生包引用映射。技能管理智能体/技能/MCP/知识库与CloudCC CLI管理CRM资源是两条开发通道。

## 5. 本地联调测试

本地Web通过OpenAPI调用已在开发CRM组织发布的自定义类，再读写对象；涉及AI时同时测试实际已发布智能体及其技能、知识库和工具行为。先确认Agent运行接口鉴权方式，AgentCiCi开发者Token不能直接代替Agent运行Key。

CRM调试身份使用项目根目录由CLI生成的.cloudcc-cache.json内对应当前环境的accessToken，配合该环境的服务地址。当前Lightning缓存按配置safetyMark（无则secretKey）选择，不是读取缓存第一项，也不能把pluginToken或AgentCiCi Token当成accessToken。缓存缺失、失效或CLI拒绝时由CLI正规刷新，不手工伪造或长期复制缓存。令牌只在本地运行时注入；浏览器无法直接读取本机缓存文件，可由本机开发进程读取并通过本地调用代理使用，不把整个缓存暴露为静态文件。OpenAPI地址、CORS和方法参数以真实环境为准。

测试正常业务、参数错误、后端失败、AI实际调用及知识检索；保留实际结果和未验证项到docs/integration-test.md。mock验证只记为模拟通过，不冒充真实CRM或AI联调。本阶段不把测试密钥/Token固化到源码或VITE_*等构建变量。

## 6. 打包、上传与组织发布

- 构建Web，仅收集运行文件；CRM对象/字段交付定义与类SOURCE内容使用平台v2业务资源契约，不能把CLI的plan或完整类目录直接当作安装定义。
- 自定义智能体和技能通过开发者接口导出完整原生包；知识库使用逻辑ref/name声明并建立绑定映射；MCP仅携带无凭据服务声明、工具名和逻辑映射，不携带开发headers、Secret、测试Token或开发组织ID。当前包不自动迁移知识文档/索引；目标组织需要按确认的资料交付范围上传、发布索引并验收。
- 按application.json的cloudccResources声明打包object/field/class，工具验证文件范围、白名单属性、依赖与摘要，保留原生包字节。示例见 [业务资源交付](ai-applications.md#cloudcc-业务资源交付)。
- check→构建→package→validate→submit→publish；release命令可串联打包、上传、创建草稿和组织发布。使用现有的权限检查；成功结果以服务端返回为准。已上传的原包可以复用submit，不覆盖同版本产物。
- 组织发布使版本可供本组织CRM安装，不等于市场上架；上传、DRAFT、PUBLISHED、CRM已安装及系统测试通过分别记录。发布请求结果未知时先get核实，不重新打包覆盖同版本或自动重放写操作。

## 7. CRM系统功能测试

在目标CRM安装或升级发布版本，通过实际创建的菜单进入应用，按requirements.md验证页面、对象读写、AI、技能、知识检索与选用的MCP工具业务效果。正式运行使用宿主/安装实例的身份，不回退本地开发Token。用户明确要求本流程只做当前测试用户的桌面业务功能测试，不安排多用户、多角色或移动端测试。

结果写入docs/system-test.md，区分通过、失败与未执行；没有CRM访问或目标接口尚未部署时列出具体待验项，不声称系统测试通过。
